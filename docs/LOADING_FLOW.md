# Grantha Explorer — Runtime Loading & Lazy-Part Loading

**Last updated:** 2026-08-17
**Status:** Living document. Deep-dive companion to `docs/DATA_FLOW.md` §5
(which gives the one-paragraph summary); this file is the authoritative,
end-to-end description of how a grantha is assembled in the browser and how
parts are lazy-loaded on demand.

**Keep this file current.** It is the single source of truth for the loading
architecture. If you change `lib/data.ts`, `hooks/useGranthaLoader.ts`,
`hooks/useEditions.ts`, `app/page.tsx`, `components/FlowReader.tsx`,
`components/TextContent.tsx`, or `components/NavigationSidebar.tsx` in a way
that affects *when or how* data is loaded, update this file in the same change
(see `AGENTS.md` / `CLAUDE.md`).

---

## 1. The big picture

```
granthas.json (generated index)  ──getAvailableGranthas──▶  index entry
                                                                │ path, editions[]
                                                                ▼
                                        loadGrantha(granthaId, editionId)
                                            │
                          ┌───────────────┬─┴───────────────────┐
                     flat single file                       multipart (envelope + parts)
                          │                                   │
                          └──────────▶ assembled Grantha ◀────┘
                                 (eager: first section only)
                                            │
                          useGranthaLoader (React Query, per-edition cache key)
                                            │
              ┌─────────────────────────────┼───────────────────────────┐
              │                             │                           │
      section-scoped               scroll sentinels               compare fan-out
      eager load                   (TextContent,                 (useEditions: part
      (page.tsx effect)            FlowReader)                   → every edition)
```

Two loading concerns are deliberately separated:

- **Initial assembly** (`lib/data.ts::loadGrantha`): resolve the edition, read
  the envelope, and eagerly fetch only the *first section's* parts so the first
  screen renders fast.
- **Lazy part loading** (`useGranthaLoader.loadPart` + trigger points): fetch
  `partN.json` on demand and merge it into the cached grantha in place.

## 2. The generated index — `public/data/generated/granthas.json`

- Regenerated by `scripts/generate-granthas-json.ts` in `prebuild` (every
  `npm run build`) and at every `npm run dev` start. **Gitignored — never edit
  by hand.**
- Loaded by `getAvailableGranthas()` (`lib/data.ts:285`). Each entry carries
  `id`, `path`, titles, `categories`, and for multi-edition granthas an
  `editions[]` array of stubs (`edition_id`, `path`, `commentary_title`,
  `commentator`, `isDefault`).
- **Every path used by the loader comes from this index** — never templated
  from a `grantha_id`/`edition_id` string (`lib/paths.ts`; `resolveGranthaPath`
  throws on unknown ids).

## 3. `loadGrantha(granthaId, editionId?)` — initial assembly (`lib/data.ts:307`)

1. **Module-level cache** — `granthaCache` (`lib/data.ts:239`), keyed
   `granthaId::editionId` (or bare `granthaId` for the default edition). A
   cached grantha is returned as-is; editions coexist in the cache (the
   substrate for side-by-side).
2. **Resolve the edition → path.**
   - Multi-edition grantha: `editions.find(edition_id)` → `isDefault` → first.
     `resolvedEditionId` = the stub's `edition_id`; `granthaPath` = its `path`.
   - Single-edition grantha: `edition_id = grantha_id`; the index `path` is
     used directly.
3. **Shape dispatch.** A path ending in `.json` is a flat single-file grantha;
   otherwise it is a multipart directory with `envelope.json` + `partN.json`.
4. **Multipart — read the envelope.**
   - `envelope.parts[]` entries are `{file, first_ref}`; each is given an `id`
     = first component of `first_ref` (e.g. `"3.1.1"` → `3`) for navigation.
   - **First-section eager load** (`lib/data.ts:380-385`): the parts that share
     the *first part's parent ref* (`dropLastRefComponent(parts[0].first_ref)`)
     are fetched up front. Grouping by the parent (not the coarse top-level id)
     stops a whole kāṇḍa/adhyāya from eager-loading; everything past section 1
     is lazy (§5).
   - Each fetched part is normalized (`normalizeCommentaries` flattens
     `commentary` / `commentaries`), stamped with `part_id`, and combined.
   - **Combine** (`lib/data.ts:415-434`): prefatory/concluding deduped **by
     ref** (a shared `0.1` maṅgalācaraṇa never lands twice → no duplicate React
     keys); passages concatenated; commentaries merged by `commentary_id`.
   - `partialGrantha` is assembled, then `nestSubcommentaries` attaches
     subcommentaries to their parent (honoring `parent_commentary_id`).
   - **Cached** and returned.
5. **Flat single file** — same normalization, merge-by-`commentary_id`,
   subcommentary nesting, and caching (single fetch of the one file).

The returned grantha is **partial** for multipart texts: `passages` cover only
the eagerly-loaded first section; `parts` holds the full envelope part list,
which is what the lazy loader iterates.

## 4. `useGranthaLoader` — the per-edition React Query wrapper (`hooks/useGranthaLoader.ts`)

One instance per `(granthaId, editionId)`. Returns `{ grantha, isLoading,
isError, error, loadPart, isLoadingPart }`.

- **Query key** `["grantha", granthaId, editionId ?? "default"]` — switching
  editions is a distinct query; the per-edition cache is what makes compare
  mode possible.
- **`placeholderData`** — while a new edition fetches, the most recent cached
  edition for the same `granthaId` stays visible (the mūla doesn't blank out
  mid-switch).
- **`staleTime` 5 min, `gcTime` 24 h** — granthas are cached long-term because
  lazy part loading mutates the cached object in place.

### `loadPart(firstRef)` — the lazy-part merge (`useGranthaLoader.ts:38-151`)

The core contract reused everywhere:

1. **Guard:** no-op when `!grantha || !grantha.parts` (edition not yet loaded).
2. **Resolve part info** from `grantha.parts` by `first_ref` (unique key).
3. **Skip if already loaded** — `isPartLoaded`: the part's `first_ref` passage
   is already present in `grantha.passages`. (This is the *completed-merge*
   guard; there is deliberately **no in-flight guard** — see §8.)
4. **Fetch** `loadGranthaPart(grantha.path, partFileName)`
   (`lib/data.ts:1515`) — note **`grantha.path` is the resolved per-edition
   path**, so lazy loads always hit the *active* edition, never the index's
   default-edition path.
5. **Merge into the cache in place** via `queryClient.setQueryData` (same key
   as the `useQuery`):
   - passages / prefatory / concluding appended (dedup by ref), stamped
     `part_id`, re-sorted (`sortPassagesByRef`);
   - commentaries merged by `commentary_id`, **including lazily-loaded
     subcommentaries nested under their parent** (a top-level id lookup alone
     would miss a subcommentary and drop its passages);
   - `nestSubcommentaries` re-run at the end so a subcommentary that loads
     before its parent still attaches correctly.
6. **Errors are swallowed** (try/catch + `console.error`) — `loadPart` never
   rejects; the part simply stays unloaded and the sentinel retries.

`isLoadingPart` toggles true only around the fetch, used by sentinels to avoid
re-entrant loads.

## 5. Lazy-loading trigger points

There are four independent triggers, all of which end in `loadPart(firstRef)`:

### 5.1 Section-scoped eager load on verse change (`app/page.tsx:233-253`)

When `verseRef` changes, `sectionPartsToLoad(parts, verseRef,
loadedFirstRefsFor(grantha), partLevelFor(structure))` (`lib/data.ts:1642`)
returns every part opening the selected *section* that isn't loaded yet, and
each is loaded. This is what makes a deep link to `6.1.2` fetch part 6. The
effect re-runs when `currentGrantha`, `verseRef`, or the chosen `loadPart`
identity changes; `sectionPartsToLoad` is idempotent on completed loads, so it
terminates.

### 5.2 Scroll sentinel — `TextContent.tsx` (`components/TextContent.tsx:71-105`)

An `IntersectionObserver` on a sentinel at the bottom of the loaded scroll
region. When it enters view and more parts exist, `nextUnloadedPartFirstRef`
(`lib/data.ts:1542`) finds the next part after the last loaded one and loads
it. Keyed by `first_ref` (not the coarse `part_id`) so a section spanning
multiple files loads them one at a time.

### 5.3 `FlowReader.tsx` — three mechanisms (`components/FlowReader.tsx`)

- **Forward sentinel** (`loaderRef`, lines 404-419): same
  `nextUnloadedPartFirstRef` pattern as TextContent, for continuous reading.
- **Previous-section preload** (lines 427-443): on mount / grantha / section
  change, load the part immediately *before* the selected section so a deep
  link always has the preceding chapter available above it. Deterministic,
  runs once per section.
- **Backward-scroll runway** (lines 446-464): when the reader scrolls within
  ~3 screen-heights of the top of loaded content, `previousUnloadedPartFirstRef`
  (`lib/data.ts:1589`) loads the prior unloaded part — the runway gives the
  fetch time to complete before the reader reaches the gap. (A top sentinel
  can't fire; an element above the clip is never "intersecting".)

### 5.4 Sidebar navigation — `NavigationSidebar.tsx`

- Selecting a section / breadcrumb / quick-jump calls
  `ensureSectionsUpToLoaded(idx)` (lines 250-256) which loads **every unloaded
  part from the top down to the target** so the list stays gap-free. Per-part
  guard: only parts whose `first_ref` passage is absent are fetched (a loaded
  section can still carry an unloaded misaligned part).

All four share the same `loadPart` prop from `page.tsx` (§6), so a single
correct loader serves every surface.

## 6. Compare mode — `useEditions` and the part fan-out

Compare mode (`?e=a,b&m=flow`, up to 3 editions) loads one grantha per active
edition via `useEditions` (`hooks/useEditions.ts`):

- **Fixed 3 slots** (`r0/r1/r2`) of `useGranthaLoader` — React hooks can't be
  called in a loop; slots beyond the active count get the default-edition query
  (cheap / cached).
- **Placeholder filtering** (lines 61-65): `useGranthaLoader.placeholderData`
  would otherwise show another edition's data in a loading column; editions
  whose stamped `edition_id` doesn't match the requested id are dropped until
  the real edition lands.
- **`loadPart` fan-out** — the key contract:

  > **`loadPart(firstRef)` loads the part into EVERY active edition.**

  All editions of a grantha share the same envelope `parts[]` boundaries
  (`first_ref`s), so "load section X" is edition-agnostic. The fan-out calls
  each active slot's *own* `loadPart` (each fetches from its resolved
  per-edition path and merges into its own cache key):
  `Promise.all(activeLoaders.map(l => l(firstRef)))`. It is memoized on the
  three inner `loadPart` callbacks (not the slot objects, which are fresh each
  render) so its identity is stable unless a part lands or the active set
  changes. Single active edition → fan-out of one → identical to today.
- **`isLoadingPart`** = `active.some(r => r.isLoadingPart)`.

**Wiring in `app/page.tsx`:**

```
const { editions: flowEditions, loadPart: flowLoadPart,
        isLoadingPart: flowIsLoadingPart } = useEditions(granthaId, editionIds);
const compareActive = mode === "flow" && flowEditions.length >= 2;
const sectionLoadPart = compareActive ? flowLoadPart : loadPart;
```

- `compareActive` is the single source of truth; `sectionLoadPart` is the
  primary loader in single-edition flow / panes, and the fan-out in compare.
- The section-scoped effect (§5.1) and `<FlowReader loadPart=…>` use
  `sectionLoadPart`; `isLoadingPart` is `flowIsLoadingPart` in compare.
- Panes / mobile / tablet layouts keep the primary `loadPart` verbatim.

Without the fan-out, lazy loads reached only the primary edition and the
secondary commentary column rendered empty past the first section (the bug
this architecture is designed to prevent).

## 7. React Query cache invariants

- **One cache entry per `(granthaId, editionId)`** — never cross-contaminate
  editions (a switch must not serve stale mūla/commentary from another
  edition).
- **Lazy merges mutate the cached object in place** through
  `setQueryData` with the *same* key — this is what makes React re-render with
  the new passages.
- `staleTime` is short relative to the 24 h `gcTime` because the cached grantha
  is being extended; re-fetches of the *index* are independent of part loads.

---

## 8. Data-shape prerequisites & correctness notes

- **`first_ref` is the load key** — parts are found, deduped, and tested for
  loadedness by `first_ref` everywhere (`sectionPartsToLoad`,
  `nextUnloadedPartFirstRef`, `loadPart`). Envelope `parts[].first_ref` must be
  unique.
- **Editions share part boundaries** — every edition of a grantha has the same
  `parts[]`; this is what makes the compare fan-out well-defined.
- **Per-edition path** — `grantha.path` is stamped from the resolved edition
  during `loadGrantha`; `loadPart` never templates a path.
- **No in-flight guard** — `loadPart` guards on the *completed* merge, not on
  an in-flight fetch. A rapid re-entry while a part is loading will re-fetch
  (pre-existing, bounded by React's batching and the sentinels' `isLoadingPart`
  guard). Don't add duplicate in-flight protection in each caller; if it ever
  matters, add one guard inside `loadPart`.
- **`loadPart` never rejects** — per-edition fetch errors are swallowed; the
  sentinel / effect simply retries on the next trigger.

- [ ] Which trigger(s) are affected (§5)? Update the matching section.
- [ ] Does the change touch the compare fan-out (§6)? Keep `compareActive` the
      single source of truth and keep the memoization on inner `loadPart`s.
- [ ] Does the change alter `first_ref` semantics, the eager-load scope (§3),
      or the cache key (§4, §7)? Those are load-bearing invariants — call them
      out explicitly.
- [ ] Update `docs/DATA_FLOW.md` §5 if the *one-paragraph* summary no longer
      matches.
