## Section 1 — What the current application actually does

### 1.1 Application shape

`grantha-explorer` is a **Next.js 16 static-export (SSG) single-page application**. `next.config.js:9`
sets `output: "export"`. There are three responsive layouts sharing one set of components:

| Layout | Width | File |
|---|---|---|
| Desktop | >1023px | `app/page.tsx:351-427` (three-column `PanelGroup`) |
| Tablet | 768–1023px | `components/TabletLayout.tsx` (text + commentary, drawer nav) |
| Mobile | <768px | `components/MobileLayout.tsx` (text full-width, drawer nav, bottom sheet) |

Layout selection is by `useMediaQuery` in `app/page.tsx:24-25` and branching at
`app/page.tsx:293-348`.

### 1.2 How the Upaniṣad collection is represented

The corpus is a set of JSON files under `public/data/library/`. **Every current text lives under
exactly one top-level directory: `upanishads/`** (verified by `find public/data/library` — only
`upanishads/` exists as a top-level category). The library contains **80 JSON files**, all of which
are either `envelope.json` or `partN.json` files (verified: no flat single-file grantha JSON exists
anywhere under `public/data/library`).

Three kinds of files exist, discriminated by an explicit `kind` field (not inferred):

1. **`grantha-envelope`** (top-level directory envelope) — e.g.
   `public/data/library/upanishads/isavasya/envelope.json:2` (`"kind": "grantha-envelope"`). Carries
   `grantha_id`, `canonical_title`, `text_type`, `language`, and an `editions[]` array of edition
   stubs. Present for exactly **3 granthas**: isavasya, mandukya, mandukya-karika (verified by
   `rg -l '"kind": "grantha-envelope"'`).
2. **`edition-sub-envelope`** (directory envelope inside an edition) — e.g.
   `public/data/library/upanishads/kena/kena-upanishad/envelope.json:2`. Carries `edition_id`,
   `grantha_id`, `structure_levels`, and `parts[]`. Present for **16 editions** (verified by count).
3. **`grantha-part`** (content file) — e.g.
   `public/data/library/upanishads/kena/kena-upanishad/part1.json:2`. Carries `prefatory_material`,
   `passages`, `concluding_material`, and `commentary`. There are 61 part files.

So the model is: **grantha → editions (1..n) → parts (1..n) → passages**. A single-edition grantha
has one edition directory (edition-sub-envelope) directly under `upanishads/<grantha>/`. A
multi-edition grantha has a grantha-envelope listing several edition sub-directories.

### 1.3 How texts are discovered and loaded

Discovery is **build-time** then **runtime**:

**Build time** — `scripts/generate-granthas-json.ts` recursively scans `public/data/library/`
(`scanDirectory()` at `generate-granthas-json.ts:48`), reads every `envelope.json` (kinds
`grantha-envelope` and `edition-sub-envelope`) and flat `.json` files carrying a `grantha_id`, and
writes `public/data/generated/granthas.json`. That file is git-ignored
(`public/data/README.md:21`) and regenerated by `prebuild` (`package.json` → `prebuild: tsx
scripts/generate-granthas-json.ts`).

**Runtime** — `getAvailableGranthas()` in `lib/data.ts:243-259` fetches
`/data/generated/granthas.json` (via `getAssetPath`, which prefixes `NEXT_PUBLIC_BASE_PATH`;
`lib/data.ts:208-215`). The hook `useAvailableGranthas()` (`hooks/useGrantha.ts:9-16`) caches it
forever (`staleTime: Infinity`, `gcTime: Infinity`).

**Content loading** — `loadGrantha(granthaId, editionId)` in `lib/data.ts:265-452`:
1. Checks an in-memory `granthaCache` keyed `granthaId::editionId` (`lib/data.ts:197-200`).
2. Resolves the grantha's `path` from the generated index (`lib/data.ts:275-280`).
3. Resolves the edition stub (default → first; `lib/data.ts:291-304`).
4. If multi-part (directory): fetches the edition's `envelope.json`, reads `parts[]`, and **loads
   only the parts whose `id` equals the first part's `id`** (i.e. only the first structural section
   initially; `lib/data.ts:333-335`).
5. If single-file: fetches the file directly.

**Lazy part loading** — subsequent parts load on demand via `loadPart(firstRef)`, which merges the
new part into the TanStack Query cache (`hooks/useGranthaLoader.ts:38-133`). A scroll sentinel in
both the reading panel (`components/TextContent.tsx:76-105`) and the sidebar
(`components/SidebarList.tsx:141-163`) loads the next part when the user scrolls near the end of
loaded content.

### 1.4 How the text hierarchy is represented

Hierarchy is driven entirely by data — `structure_levels` (recursive, with Devanagari/Roman
`scriptNames` per level) and dot-separated numeric passage refs (`lib/data.ts:32-39`,
`lib/data.ts:113-119`). The number of ref segments matches the depth of `structure_levels`.

Examples observed:
- Kena: `खण्डः → मन्त्रः` (2 levels), refs `1.1` (`kena/kena-upanishad/envelope.json:6-22`).
- Bṛhadāraṇyaka: `अध्यायः → ब्राह्मणम् → मन्त्रः` (3 levels), refs `3.1.1`
  (`brihadaranyaka/brihadaranyaka-upanishad/envelope.json:6-31`).
- Taittirīya: `वल्ली → अनुवाकः → मन्त्रः`, refs `1.1.1` (`taittiriya/.../envelope.json:6-31`).

The sidebar builds a flat, accordion-free model (`getSidebarFlatModel` in `lib/data.ts:784-806`,
`getPassageHierarchy` at `lib/data.ts:560-678`) with sticky section headings whose segments are
tappable breadcrumb popups (`components/SidebarList.tsx:343-395`).

### 1.5 How navigation between texts works

**Text switching** — the `GranthaSelector` dropdown (`components/GranthaSelector.tsx`) lists all
granthas by Devanagari title. Selecting one calls `onSelect(granthaId)` →
`handleGranthaChange` in `app/page.tsx:197-199` → `updateHash(newGranthaId, "1")`.

**Verse navigation** — sidebar click, prev/next buttons, quick-jump, and cross-reference links all
go through `onVerseSelect(ref)` → `updateHash(granthaId, ref, editionId)` (`app/page.tsx:202-208`).

**Edition switching** — `CommentarySelector` (`components/CommentarySelector.tsx`) →
`onEditionChange(editionId)` → `updateHash(granthaId, verseRef, newEditionId)`
(`app/page.tsx:211-213`).

### 1.6 How the "Upaniṣadaḥ" title is generated/rendered

It is **hardcoded** in `components/AppWordmark.tsx:19`:

```tsx
<span className="text-gray-500 font-normal">उपनिषदः</span>
```

The full wordmark `ग्रन्थपरिशीलकः > उपनिषदः` is a static rendering. There is no mechanism to vary
the second segment. `AppWordmark` is rendered in the desktop left sidebar (`app/page.tsx:360-366`,
via `NavigationSidebar` with `showWordmark`), and in the mobile/tablet headers
(`components/MobileLayout.tsx:108`, `components/TabletLayout.tsx:121`). The HTML `<title>` is
"Grantha Explorer" (`app/layout.tsx:25`); the meta description is Upaniṣad-specific
(`app/layout.tsx:27`: "Explore classical Upanishad texts with Sanskrit commentary in an interactive
reader").

### 1.7 How routing and URL state work

Hash-based. Format: `#granthaId:verseRef?e=editionId&co=1`. Parsing/building is in
`lib/hashUtils.ts` (`parseHash` at `:25`, `buildHash` at `:95`). The hash is the **sole source of
truth** for navigation state, managed by `hooks/useVerseHash.ts`:
- Listens to `hashchange` (`useVerseHash.ts:79-105`) so browser back/forward works for free.
- `updateHash` (`useVerseHash.ts:108-150`) — resets the edition when the grantha changes.
- On first load with **no hash**, it writes a default hash and forces the first grantha
  (`useVerseHash.ts:61-73`):

  ```ts
  const initialHash = buildHash({ granthaId: defaultGranthaId, verseRef: defaultVerseRef, commentaryOpen: false });
  window.history.replaceState(null, "", initialHash);
  ```

  The default grantha is `granthas[0]?.id || "isavasya-upanishad"` (`app/page.tsx:63`).

**Base path** — in production the app is served under `/grantha-explorer` (`next.config.js:13-14`);
`getAssetPath` prepends `NEXT_PUBLIC_BASE_PATH` to all fetch URLs (`lib/data.ts:208-215`).

### 1.8 How selection state is maintained

- **Core navigation state** (grantha, verse, edition, commentary-open): URL hash only
  (`useVerseHash.ts`).
- **Validation**: `validateAndNormalizeHash` (`lib/hashUtils.ts:218-260`) corrects invalid refs /
  editions; a modal (`InvalidVerseModal`) is shown and the URL corrected (`app/page.tsx:131-160`).
- **Transient UI state** (not in URL): panel sizes in `localStorage`
  (`app/page.tsx:37-46`, `components/TabletLayout.tsx:49-58`), scroll positions via refs.
- **Commentary-open** (`co=1` param) drives the mobile bottom sheet.

### 1.9 How the UI determines which texts are available

Availability = intersection of:
1. Data files present under `public/data/library/` (indexer discovers them),
2. A metadata entry in `public/data/granthas-meta.json` (the indexer filters
   `granthas-meta.json` keys against discovered paths; `generate-granthas-json.ts:155-166`),
3. Inclusion in the generated `granthas.json` (`lib/data.ts:243-259`).

`granthas-order.json` controls **display order only**, not inclusion. The indexer sort places
ordered IDs first, then falls back to alphabetical `title` comparison
(`generate-granthas-json.ts:168-182`).

### 1.10 Existing abstractions that could naturally support categories

- **The indexer is category-agnostic.** `scanDirectory()` (`generate-granthas-json.ts:48-151`)
  recursively scans without discriminating on directory names; a text under
  `library/smritis/manu/` would be discovered identically to one under `library/upanishads/kena/`.
- **`text_type` exists in the data schema** — `grantha.schema.json:38-41` and
  `grantha-envelope.schema.json:22-25` declare it (enum: upanishad, smriti, sutra, purana, stotra,
  other). It is present in the **3 grantha-envelopes** (all currently `"upanishad"` — verified at
  `isavasya/envelope.json:6`, `mandukya/envelope.json`, `mandukya-karika/envelope.json`).
- **`Grantha.text_type` field exists** in the runtime type (`lib/data.ts:109`).
- **`GranthaSelector` renders any `GranthaMetadata[]`** — no type-specific logic
  (`components/GranthaSelector.tsx`).
- **The `script`/`language` fields** (`lib/data.ts:110-111`) already vary per grantha.

### 2.2 Contradictions surfaced (not silently resolved)

> **CONTRADICTION 1 — `text_type` enum vs. actual data.**
> `grantha.schema.json:40` and `grantha-envelope.schema.json:24` declare `text_type` enum
> `["upanishad", "smriti", "sutra", "purana", "stotra", "other"]`. The source corpus
> (`../grantha-data/structured_md`) uses values **`brahma-sutra-bhashya` (48 files),
> `gita-bhashya` (19 files), `prakarana` (1 file), `upanishad` (109 files)** — three of which are
> **absent from the enum**. The schemas are stale relative to the data they describe. Assessment:
> the schema enum must be widened (or `text_type` made an open string) before Rāmānuja works are
> exposed.

> **CONTRADICTION 2 — `text_type`/`tags`/`author` exist in source but are dropped before the app.**
> `../grantha-data/structured_md` frontmatter carries `text_type` on all 177 content files,
> `tags` on 110, and `author` on 68 (see Section 2.3). But `scripts/convert_structured_md.py`
> `build_part_json` (`:662-737`) and `build_envelope_json` (`:737-760`) emit **none** of these into
> the JSON output (output carries only kind/schema_version/grantha_id/edition_id/part_num/structure/
> parts/passages/commentary). And the indexer `generate-granthas-json.ts:155-166` maps only
> id/path/title/title_deva/title_iast/editions. Net effect: even though the reference design
> assumes `text_type` is "already in the data," it is not present in the runtime-facing index at
> all. This is the single most consequential data finding.

> **CONTRADICTION 3 — schema says single-file granthas exist; library has none.**
> `grantha.schema.json` describes a flat single-file grantha (`kind: "grantha"`), and
> `loadGrantha` implements a single-file path (`lib/data.ts:425-447`), but the library contains no
> such file. Assessment: the flat path is currently unreachable; either it stays as latent support
> for future single-file granthas or the schema/loader will be needed when flat texts (e.g.
> Vedārtha Saṅgraha if published as a single file) arrive.

| File | `tags` value(s) |
|---|---|
| `upanishads/isavasya/isavasya-upanishad-sankara-bhashya-01.md` | `upanishad` |
| `upanishads/kena/kena-upanishad-rangaramanuja.md` | `upanishad` |
| `upanishads/mandukya/mandukya-upanishad-sankara-bhashya-01.md` | `upanishad` |
| `upanishads/brihadaranyaka/brihadaranyaka-upanishad-sankara-bhashya-01.md` | `upanishad` |
| `upanishads/prashna/prashna-upanishad-rangaramanuja-01-01.md` | `upanishad` |
| `upanishads/svetasvatara/svetasvatara-upanishad-rangaramanuja-01-01.md` | `upanishad` |
| `upanishads/taittiriya/taittiriya-upanishad-sankara-bhashya-01.md` | `upanishad` |
| `vedarthasangraha/vedarthasangraha-01.md` | `prakarana`, `upanishads`, `vedas` |

**Assessment — tags read as bibliographic/collection-like, not thematic/topical:**

- **Every Upaniṣad file** (109/109, verified exhaustively) carries exactly one tag: `upanishad`.
  That value is **redundant with `text_type`** (already `upanishad` on all of them) and is a
  genre/collection label, not a philosophical/topical descriptor (no terms like brahman, ātman,
  mokṣa, karma, etc. appear anywhere).
- **The only multi-tag file** is Vedārtha Saṅgraha with `[prakarana, upanishads, vedas]` — a mix of
  genre (`prakarana`), corpus membership (`upanishads`), and scriptural class (`vedas`). Still
  bibliographic; not topical.
- **Distinct tag vocabulary across the whole corpus is only 4 values** (`upanishad`, `prakarana`,
  `upanishads`, `vedas`), and 110 of 177 files (62%) carry tags at all. This is not a real
  faceting vocabulary.

**Conclusion for Phase 2:** `tags` are **not a v1 category candidate.** They are (a) absent on all
Rāmānuja works, (b) redundant with `text_type` where present, and (c) bibliographic rather than
thematic. They remain a **v2 search-facet candidate at best**, and only if the corpus later gains
enriched topical tags. They should not be the basis of the v1 categories field.

### 2.5 The category-key decision: does Phase 1 evidence support the "explicit field" framing?

**Framing to assess:** `author` and `tags` have disjoint, non-overlapping coverage, so deriving the
category key live from either field is untenable; an explicit, independently-maintained categories
field (bootstrapped using `author` as a heuristic where available, not derived from it at build
time) is the right call.

**Phase 1 evidence — supports the framing, with one nuance:**

- **Correct:** neither field alone covers the corpus (author 38%, tags 62%). Any live derivation
  from a single field would leave 38–62% of texts uncategorized. Verified exhaustively (§2.3).
- **Nuance (contradicts strict "disjoint"):** the fields are *not* perfectly disjoint — exactly one
  file (Vedārtha Saṅgraha) carries **both** `author` and `tags`. So "disjoint" is imprecise; the
  accurate statement is "almost disjoint, with a single point of overlap at
  `vedarthasangraha/vedarthasangraha-01.md`." This does not weaken the conclusion — it strengthens
  it, because the one overlapping file is precisely a case where author-derived and tag-derived
  category keys would disagree about how to group the text.
- **Supports explicit, independent field:** because `author` (38%) and `tags` (62%) are both
  partial and heterogeneously populated, and because the user-facing category concepts
  ("Upaniṣadaḥ", "Rāmānuja's works") do not map 1:1 onto either field, Phase 1 confirms that the
  **categories key must be explicit and independently maintained** — populated by a curated mapping
  (`grantha_id → categories[]`), *not* derived at build time from `author`/`tags`/`text_type`.
- **Supports "author as bootstrap heuristic":** `author: भगवद् रामानुजः` cleanly identifies all 68
  Rāmānuja files. Using it as a *one-time bootstrap heuristic* to seed the initial curated mapping
  (i.e. to suggest "these 5 grantha_ids → ramanuja") is sound, because it is uniform across the
  Rāmānuja subset. But the resulting mapping must be **curated and frozen in config**, not
  recomputed per build — because (a) future works without an `author` field must still be
  classifiable, and (b) the field is absent on Upaniṣads by design, so the build must not depend on
  it.

**Phase 1 verdict:** the explicit-categories-field framing is **supported** by the evidence, with
the single precision that coverage is "almost disjoint" (one overlap) rather than strictly
disjoint. This is the framing Phase 2 must adopt.

**Sampling coverage (structured_md):** directory inventory exhaustive (all 4 categories, all
subdirs). Frontmatter fields (`text_type`, `tags`, `author`, `structure_type`) counted exhaustively
over all 177 content files via `rg`. The `author`/`tags` per-file overlap was computed exhaustively
over all 177 files (§2.3, §2.5). Actual `tags` values sampled from 8 files (§2.4). Deep file reads
(frontmatter + structural markers): 8 files — isavasya (śaṅkara), kena (raṅgarāmānuja),
sribhashya-01-01, gitabhashya-01, vedarthasangraha-01, brihadaranyaka (SOURCE_ISSUES + one part),
vedanta-deepam-01-01, vedanta-sara-01-01.
⚠️ **UNVERIFIED:** the *body* structure of non-sample part files (passage numbering, commentary
block placement) was not read for every file; claims in §2.3 about structure are limited to the
files listed above plus the aggregate frontmatter counts. No claim about body content is extended
beyond sampled files.

## Section 8 — What needs to change conceptually in the loading/navigation architecture

This section surveys the architecture areas the plan asked about and identifies the **minimum
conceptual changes** — not implementation details.

### 8.1 File discovery

**Currently:** recursive `scanDirectory()` in `generate-granthas-json.ts:48-151` finds any
envelope/part JSON under `library/`. It is already category-agnostic.

**Conceptual change:** none required for discovery itself. A new category arrives simply by adding
its directory tree under `public/data/library/` (e.g. `library/ramanuja/sribhashya/...`). What must
change is *what the indexer records about each discovered text* (see 8.2).

### 8.2 Manifests / indexes

**Currently:** `granthas.json` entries carry `id/path/title/title_deva/title_iast/editions` only
(`generate-granthas-json.ts:155-166`). `granthas-order.json` is a flat 14-ID array.

**Conceptual change:** the index entry must carry a **category/tag key per text** so the UI can
group/filter without loading full grantha data. Two options:

- **(a) Reuse `text_type`** — but §2.2 CONTRA 2 shows it never reaches the runtime index today, and
  it is a poor fit for the user's category concepts (Rāmānuja's works span 3 different `text_type`
  values). 
- **(b) Add an explicit category/tags field** derived at build time from a mapping (path-prefix or
  explicit grantha_id → categories). This is the minimum change that matches the "categories are
  overlapping tags" requirement from the brief.

Either way, the schema `text_type` enum must be widened or relaxed (CONTRA 1).

### 8.3 Routing

**Currently:** hash `#granthaId:verseRef?e=editionId`; empty hash is overwritten with a default
(`useVerseHash.ts:61-73`).

**Conceptual change:** routing must support a **"no grantha selected" state** (landing page). That
means the hash parser/routing must tolerate an empty hash and the `useVerseHash` return type must
become nullable (`granthaId: string | null`, `verseRef: string | null`). Category itself need **not**
be in the URL (it is derivable from the selected text), which preserves deep-link behavior.

### 8.4 Loading

**Currently:** `loadGrantha` is keyed on `granthaId + editionId`; `useGranthaLoader` requires a
`granthaId: string` (`useGranthaLoader.ts:14-36`).

**Conceptual change:** the loader must be **guarded against a null/absent grantha** (disable the
query when no text is selected — e.g. an `enabled` option or a caller-level guard). Content loading
itself is category-agnostic and needs no structural change.

### 8.5 State management

**Currently:** all core state in the URL hash; transient UI state in `localStorage`.

**Conceptual change:** add one piece of **non-URL state** — the active category filter
(`selectedCategoryId`) for the landing page. It is explicitly a transient browsing filter, not
part of the shareable URL (consistent with "category derivable from text, not stored").

### 8.6 Text metadata

**Currently:** `GranthaMetadata` has no category/tags field (`lib/data.ts:123-131`).

**Conceptual change:** add category (or tags) to `GranthaMetadata` so the list-display layer can
group/filter. Also, `text_type` needs to be *actually delivered* to the runtime if the wordmark is
to show text type (CONTRA 2: it is dropped today). Both are additive, non-breaking changes to the
index.

### 8.7 Navigation

**Currently:** flat grantha selector list; no sections/chips; category switching is not a concept.

**Conceptual change:** the text list needs a category-filter interaction (chips on the landing
page, per the settled direction). The reading view's own grantha selector can remain a flat list.
No change is required to the verse/section navigation machinery (sidebar, prev/next, quick-jump),
which is category-agnostic.

### 8.8 Components

**Currently:** `AppWordmark` is static; there is no `LandingPage`; all layouts assume a loaded
grantha.

**Conceptual change:** (a) `AppWordmark` becomes dynamic (shows text-type or category label + brand
as home link); (b) a new landing component is introduced; (c) `page.tsx` branches on
"grantha selected vs not." These are new UI responsibilities, not rewrites of existing reading
components.

### 8.9 URL construction

**Currently:** `buildHash` always requires a granthaId+verseRef (`lib/hashUtils.ts:95-144`).

**Conceptual change:** support building/clearing to the empty hash (landing state). No category in
the URL.

### 8.10 Caching

**Currently:** TanStack Query caches `["grantha", granthaId, editionId]` (`useGranthaLoader.ts:21`)
and `["granthas"]` (`useGrantha.ts:11`), plus an in-memory `granthaCache` (`lib/data.ts:197-200`).

**Conceptual change:** none required. Category filtering operates on the already-cached granthas
list; no new cache key or invalidation model is needed. The disabled loader when no grantha is
selected simply has no query.

### 8.11 Search / filtering

**Currently:** no search; filtering is not implemented (`DESIGN.md:167` — "No search" in v1 scope).

**Conceptual change:** category chips are the v1 filtering surface. Multi-tag / keyword search is
explicitly deferred (DESIGN.md scope), but the data model should not preclude it — hence an
array-valued category/tags field on `GranthaMetadata` is preferable to a single string.

### 8.12 Ordering

**Currently:** `granthas-order.json` flat ordering + alphabetical fallback
(`generate-granthas-json.ts:168-182`).

**Conceptual change:** the "all texts" view needs a stable order that is category-aware (group by
category, order within category). This can be an evolution of `granthas-order.json` (grouped) or a
category-order list in the new category config. Not a blocking change, but must be decided with the
config schema.

### 8.13 Minimum conceptual change summary

| Area | Change needed? | Nature |
|---|---|---|
| File discovery | No | already generic |
| Manifests/indexes | **Yes** | add category/tags to index entries; widen `text_type` enum |
| Routing | **Yes** | nullable hash state, empty-hash = landing |
| Loading | **Yes** | guard loader against absent grantha |
| State management | **Yes** | add transient category-filter state |
| Text metadata | **Yes** | add category/tags to `GranthaMetadata`; deliver `text_type` to runtime |
| Navigation | **Yes** | category-filter interaction on landing list |
| Components | **Yes** | dynamic wordmark, landing page, page.tsx branch |
| URL construction | **Yes** | support empty-hash (landing) |
| Caching | No | none required |
| Search/filtering | Partial | chips only (v1); tags array keeps v2 search open |
| Ordering | **Yes** | category-aware ordering for the all-texts view |

The architecture already generalizes well for content loading and hierarchy. The changes cluster in
the **index/type layer** (category metadata) and the **app-shell layer** (landing vs reading
states) — not in the reading engine itself.

## Section 9 — Important edge cases

These are surfaced from the investigation (not design proposals). They will constrain Phase 2.

### 9.1 Texts that don't fit the existing structural model

- **Flat prose text (Vedārtha Saṅgraha).** `structure_levels` is a single level (`पाठः`), refs are
  `0.1, 0.2, 1..252` (`vedarthasangraha-01.md:1-22`). The sidebar flat model handles `depth <= 1`
  (`lib/data.ts:791-792`), so this already renders. **Not a blocker** — but it is the first
  non-verse-style text and should be load-tested when ingested.
- **Four-level structure (Śrībhāṣyam).** Depth-4 (`अध्यायः→पादः→अधिकरणम्→सूत्रम्`) exceeds the
  deepest current Upaniṣad (depth 3, Bṛhadāraṇyaka). The recursion in `getPassageHierarchy`
  (`lib/data.ts:570-611`) and `collectSections` (`lib/data.ts:730-782`) is data-driven and has no
  hard depth cap, but **depth-4 breadcrumb popups and sticky headings are unexercised** —
  ⚠️ UNVERIFIED until a depth-4 text is actually loaded.
- **Mūla-only parts with no commentary** (e.g. kaushitaki adhyāya 2 in source). The commentary
  panel already handles "no commentary" (`components/CommentaryPanel.tsx:193-206`).

### 9.2 Paths that assume a single collection

- **Flat single-file loader is dead code today** (`lib/data.ts:425-447`) because no flat files
  exist (CONTRA 3). If Rāmānuja texts are published as flat single files (possible for Vedārtha
  Saṅgraha), this path activates for the first time and is **untested in production**.
- **`granthas-order.json` is Upaniṣad-only**; a category-aware ordering must be designed before the
  all-texts landing list can be ordered sensibly.

### 9.3 Browser back/forward, refresh, and deep-link behavior

- **Deep link to `#sribhashya:1.1.1`** (once ingested) must resolve through `loadGrantha` exactly
  like an Upaniṣad — it is category-agnostic. The verse-validity modal flow
  (`app/page.tsx:131-160`) applies unchanged.
- **Empty-hash landing state must not be "fixed" by writing a default hash.** Today
  `useVerseHash` overwrites an empty hash (`useVerseHash.ts:61-73`); the landing-first design
  requires the opposite (empty hash = landing). Back/forward between landing and a reading state
  must therefore produce the correct non-null/null grantha transitions.
- **Refresh on landing** must restore the landing page (no default text forced).
- **Category filter is not in the URL** → refreshing on the landing page loses the active chip
  (acceptable; it is a transient filter). This must be stated explicitly as a known tradeoff.

### 9.4 Missing or incomplete metadata

- **A text with no category assignment** must still appear somewhere (e.g. an implicit "all/other"
  bucket) so it is not undiscoverable.
- **A text with unknown/absent `text_type`** — since `text_type` currently never reaches the
  runtime for single-edition texts (CONTRA 2), any wordmark or display that depends on it will show
  **nothing** unless the pipeline is fixed. This is the highest-risk edge case for the design.
- **`title_deva` fallback**: `loadGrantha` falls back to `granthaMetadata.title_deva` when
  `canonical_title` is absent (`lib/data.ts:384-386`); the landing list should use the same
  fallback chain so no text shows a blank title.

### 9.5 Validation integrity

- `npm run build` runs `validate:integrity` on **10 specific Upaniṣad directories** hardcoded in
  `package.json`. New categories are **not validated** by the current build. Either the validate
  step must be generalized or new categories need their own validation wiring.

## Section 3 — What the new multi-category mental model should be

### 3.1 The four concepts, grounded in evidence

The reference design's mental model holds up, but Phase 1 sharpens it with concrete data. The user
needs to distinguish exactly four things:

| Concept | What it is | Data anchor (Phase 1) |
|---|---|---|
| **Category** | User-facing grouping; a text may belong to many; used for discovery/filter | explicit `categories` field (Phase 1 §2.5 verdict) |
| **Work / Text** | A single grantha the user opens and reads | `grantha_id` / index entry (`granthas.json`) |
| **Structural subdivision** | In-text hierarchy, already data-driven | `structure_levels` + dot refs (`lib/data.ts:32-39`) |
| **Text type** | Intrinsic property used by the wordmark | `text_type` — **but see §3.2** |

### 3.2 ⚠️ Stress-test finding: the wordmark-from-`text_type` premise is broken today

The reference design makes the wordmark show `text_type` ("उपनिषत्", "ब्रह्मसूत्रभाष्यम्"). Phase 1
shows this data **does not reach the app for 10 of 13 texts**:

- `text_type` is present in only the **3 grantha-envelopes** (`isavasya`, `mandukya`,
  `mandukya-karika` — verified at `public/data/library/upanishads/*/envelope.json`).
- It is **absent from all 16 edition-sub-envelopes and all 61 part files** (verified: 0 matches).
- The indexer (`generate-granthas-json.ts`) never reads it; `granthas.json` carries no `text_type`.

So the 10 single-edition Upaniṣads (kena, katha, prashna, mundaka, taittiriya, aitareya, chandogya,
brihadaranyaka, kaushitaki, svetasvatara) have **no `text_type` anywhere in the runtime-facing
data**. The reference design assumed "resolve text_type into text_type_display" in the indexer — but
the indexer has nothing to resolve from for those texts.

**Three ways to close this, in ascending effort:**

- **(i) Put `text_type` into `categories.json`** per grantha_id (alongside `text_categories`). The
  indexer stamps it. Zero converter changes. **REJECTED by decision (2026-08-11):** it is a
  "shadow-map" that duplicates data the converter already has and would drift from the source of
  truth.
- **(ii) Fix the converter** (`scripts/convert_structured_md.py` `build_envelope_json` at `:737`) to
  emit `text_type` into edition-sub-envelopes (it already has `frontmatter["text_type"]` available),
  propagate it through the schema, and have the indexer read it. Requires regenerating the affected
  envelopes. **ACCEPTED by decision (2026-08-11)** — see Section 11, Step 1. Since Rāmānuja
  ingestion is in scope and touches the converter anyway, this is the real fix.
- **(iii) Wordmark shows category instead of text type.** Avoids the problem but re-introduces the
  multi-category ambiguity the reference design explicitly rejected (§1 of the draft).

**Resolution:** **(ii)** — converter → schema → indexer. The shadow-map approach (i) is deleted
from this design. See Section 11 for the sequencing.

### 3.3 The mental model, stated

> "I open Grantha Explorer and land on the library. I can filter by category (उपनिषदः,
> रामानुजश्रीसूक्तयः) to narrow the list, or just scan everything. I open a work and read it. The
> wordmark tells me what kind of text I'm reading. The brand takes me back to the library."

This is correct and the reference design's §1 wording stands. No revision needed beyond the `text_type`
source fix in §3.2.

## Section 4 — Assessment of the "click उपनिषदः" idea

The original proposal was: make the wordmark's `उपनिषदः` clickable to switch category. Phase 1
evidence supports **rejecting** it, and the settled design already replaced it with something better.

### 4.1 Why the evidence rejects it

- **The wordmark is static branding, not a control.** `AppWordmark` is a pure presentational span
  (`components/AppWordmark.tsx:10-21`); making the second segment a category switcher conflates brand
  identity with navigation.
- **The category isn't the right thing to display there anyway.** The reference design's deeper
  insight (which Phase 1 §3.2 keeps) is that the wordmark should show the *type* of the current text,
  not its *category* — because a text in multiple categories has no single category label.
- **The interaction target is already claimed.** In the settled design the *brand word*
  `ग्रन्थपरिशीलकः` becomes the "return to library" home link, and category selection lives on the
  landing page chips. Making `उपनिषदः` a category switcher would duplicate that role with a worse
  affordance.

### 4.2 Verdict

**Reject** "click उपनिषदः → change category." Replace with: wordmark second segment = text type
(needs the §3.2 source fix), brand word = home, category selection = landing-page chips. This is a
strictly better decomposition: one concept per surface, no ambiguity, and it scales to many
categories without rethinking the wordmark.

## Section 5 — 2–4 alternative UX approaches

All four approaches below are evaluated against the same criteria. Phase 1 citations are used where
the evidence decides a point.

### 5.1 Approach A — Landing page + chips (the reference design, stress-tested)

The app default state is a landing/library page with category chips (outlined pills, single-select,
no chip = all) and a flat text list; selecting a text enters the reading view; the brand word in the
reading view returns to the library.

| Criterion | Assessment |
|---|---|
| Mental model | Clear: "library, then reading." Matches scholar workflow |
| Discoverability | High — categories are the first thing visible |
| Scalability | Good — chips row + scrollable list handle many categories |
| Interaction cost | One click to filter + one to open a text (only when filtering); zero-cost deep links |
| Visual complexity | Low — one new surface, existing reading view unchanged |
| URL / deep-link | Category not in URL (derived); deep links bypass landing (Phase 1 §1.7, §9.3) |
| Relation to existing UI | Adds a landing layer; reading engine untouched (Phase 1 §8.13) |
| Implementation complexity | Medium — new component + nullable hash state + wordmark |
| Future categories | Best — adding a category = config entry + data dir (Phase 1 §2.5, §8.11) |

### 5.2 Approach B — Chips inside the reading-view grantha selector

Category chips appear in the existing `GranthaSelector` popup; no separate landing page. The app
still boots directly into a text.

| Criterion | Assessment |
|---|---|
| Mental model | "Categories are a filter in the picker" |
| Discoverability | Lower — hidden inside the picker popup |
| Scalability | Good |
| Interaction cost | Low |
| Visual complexity | Low |
| URL / deep-link | Same as today; no landing state needed |
| Relation to existing UI | Least disruption — touches only the picker |
| Implementation complexity | Lowest |
| Future categories | Good |

**Why Phase 1 evidence weakens this:** the user explicitly decided "chips on the landing page only"
during iteration, and DESIGN.md's primary persona is a *sustained reader* who benefits from a
first-class library surface. More importantly, the settled direction (#4 in the draft) is
"landing page is the default entry point" — a deliberate change B would not deliver.

### 5.3 Approach C — Dedicated category browsing page (multi-step)

A full intermediate page between landing and reading: landing → category page (list of works in a
category) → reading.

| Criterion | Assessment |
|---|---|
| Mental model | "Folder → folder → file" |
| Discoverability | High |
| Scalability | Good |
| Interaction cost | **Highest** — extra step before reading |
| Visual complexity | High — another page + back affordance |
| URL / deep-link | Category becomes a URL segment; deep links still bypass |
| Relation to existing UI | Most disruption |
| Implementation complexity | Highest |
| Future categories | Good |

**Why rejected:** it adds a mandatory step that Phase 1 does not justify. DESIGN.md:33 asserts most
sessions begin at a deep link; a mandatory browse step contradicts that. The flat list + chips
already covers "browse a category" in one click.

### 5.4 Approach D — Clickable wordmark only (the user's original idea)

No landing page; the `उपनिषदः` in the wordmark opens a category switcher.

| Criterion | Assessment |
|---|---|
| Mental model | Ambiguous — is the title a page, a breadcrumb, or a menu? |
| Discoverability | Poor — no visual affordance for "click the title" |
| Scalability | Poor — categories hidden behind one small target |
| Interaction cost | Low per switch, but never discoverable |
| Visual complexity | Low |
| URL / deep-link | No landing state |
| Relation to existing UI | Minimal |
| Implementation complexity | Low |
| Future categories | Poor |

**Why rejected:** Section 4 covers this in full.

### 5.5 Recommendation from the comparison

**Approach A** wins on discoverability + scalability + future-category fit, at an acceptable
implementation cost. The stress-test corrections (§3.2 text_type source; §2.5 explicit categories)
are folded into Section 6.

## Section 6 — Recommended approach

Adopt **Approach A** (landing page + chips + brand-as-home), with the following Phase 1-driven
revisions to the reference design:

1. **`text_type` source fix** (§3.2, resolved): the **converter → schema → indexer** path carries
   `text_type` (option ii). The shadow-map approach is rejected/deleted (decision 2026-08-11). The
   wordmark's `text_type_display` is resolved by the indexer from the library data via
   `text_type_labels`, not from a per-grantha config map.
2. **`categories` field confirmed explicit** (§2.5): `text_categories` in `categories.json` is the
   curated, independently-maintained mapping. Bootstrapped once from `author: भगवद् रामानुजः`
   (68 files → 5 works) as a heuristic, then frozen — never derived at build time.
3. **Rāmānuja ingestion is in scope** for this workstream (decision 2026-08-11): the 5 works are not
   in `public/data/library/` today and their meta keys do not match source ids (`sribhashya` vs
   `sri-bhashya`; `gita-bhashyam` vs `gita` — see Section 11, Step 3). The file-change list is split
   into **data-ingestion work** and **UI work** (§6.3).
4. **Validation wiring** (Phase 1 §9.5): `package.json` `validate:integrity` is Upaniṣad-hardcoded;
   new categories need generalized validation.

### 6.1 Recommended `categories.json` shape (revised)

No shadow-map. `categories.json` holds only category definitions, text-type display labels (for the
wordmark's label lookup), and text→category assignments. `text_type` itself comes from the library
data via the converter fix.

```jsonc

  "text_type_labels": {
    "upanishad": { "deva": "उपनिषत्" },
    "brahma-sutra-bhashya": { "deva": "ब्रह्मसूत्रभाष्यम्" },
    "gita-bhashya": { "deva": "गीताभाष्यम्" },
    "prakarana": { "deva": "प्रकरणम्" }
    // other text_type values can be added as new works arrive
  },
  "text_categories": {
    "isavasya-upanishad": ["upanishads"],
    "kena-upanishad": ["upanishads"],
    // ... all current upanishads ...
    "sribhashya": ["ramanuja"],
    "vedanta-deepam": ["ramanuja"],
    "vedanta-sara": ["ramanuja"],
    "gita-bhashyam": ["ramanuja"],
    "vedarthasangraha": ["ramanuja"]
  }
}
```

⚠️ **UNVERIFIED / open item:** the grantha_id keys for Rāmānuja works depend on the exact ids used
in `granthas-meta.json` and the ingested `library/` build. Phase 1 shows source ids (`sribhashya`,
`gita-bhashyam`) differ from existing meta keys (`sri-bhashya`, `gita`) — the config must use the
**post-ingestion** ids. Section 11, Step 3 resolves this.

> **Note (post-§11.4 revision):** this §6.1 example predates the scope-update that added mūla Gītā
> and mūla Brahma Sūtra. §11.4 supersedes it with the **work-family** category model:
> `upanishads`, `gita`, `brahma-sutra`, `ramanuja` (with overlapping assignments, e.g.
> `gita-bhashyam: ["gita", "ramanuja"]`), plus `text_type_labels` entries for the mūla types
> (`smriti`→स्मृतिः, `sutra`→सूत्रम्). Treat §11.4 as authoritative.

### 6.2 Revised `GranthaMetadata` and indexer

```typescript
export interface GranthaMetadata {
  id: string;
  path: string;
  title: string;
  title_deva: string;
  title_iast: string;
  editions?: EditionStub[];
  categories: string[];        // NEW — stamped from categories.json text_categories
  text_type_display?: string;  // NEW — resolved by indexer from library text_type via text_type_labels
}
```

Indexer: read `categories.json` for `text_categories` (→ `categories`, default `[]`) and
`text_type_labels` (→ label lookup). `text_type` itself is read from the **library data** (now
present after the converter fix), and `text_type_display` is resolved via `text_type_labels`
(fallback: omit the field). This differs from the draft only in **where `text_type` comes from**
(library JSON, via the pipeline fix — not a config shadow-map).

### 11.1a Investigation: does structured_md contain mūla Gītā / mūla Brahma Sūtra?

**Question:** Does `../grantha-data/structured_md` contain standalone mūla Gītā or mūla Brahma
Sūtra content?

**Answer: NO — this is a sourcing gap, not merely an ingestion task.** Verified:

- **Top-level directory inventory (exhaustive, 3 levels):** the only directories under
  `structured_md/` are `upanishads/`, `bhagavad-gita/` (containing only `gitabhashya/`),
  `brahma-sutras/` (containing only `sribhashya/`, `vedanta-deepam/`, `vedanta-sara/`), and
  `vedarthasangraha/`. There is **no mūla-only directory** for Gītā or Brahma Sūtra.
- **Files outside those categories:** only the root `README.md` (a content-validation doc, not a
  text). No mūla Gītā, no mūla Brahma Sūtra file anywhere.
- **`sources/` (grantha-data repo):** contains only Upaniṣad sources (`sources/upanishads/vishvas`,
  `sources/upanishads/meghamala`). No Gītā or Brahma Sūtra mūla source present.
- **Git history (whole grantha-data repo):** no commit ever added a standalone mūla Gītā or mūla
  Brahma Sūtra file (searched `--all` history; only the bhāṣya imports exist).

**Is the mūla recoverable from the bhāṣya files?**

- **Gītā bhāṣya embeds the mūla verse per passage.** In `gitabhashya`, each `# Verse A.B` passage
  contains the mūla śloka (short numbered lines ending `॥ N ॥`) followed by Rāmānuja's prose in the
  **same** `sanskrit:devanagari` block (verified: `gita-bhashyam-02.md` Verse 1.1, 1.2…; no separate
  `# Commentary:` marker exists — the converter merges mūla + bhāṣya into one passage). The converter
  (`tools/scripts/gitabhashya_converter/convert_gitabhashya.py`) *internally* distinguishes "short
  numbered mūla line" from "long bhāṣya prose" (length-cap heuristic at `:79`), so the mūla is
  **theoretically extractable but not cleanly separated in the files**.
- **Brahma Sūtra bhāṣya embeds the sūtra mūla inline.** In `sribhashya`, the sūtra text appears as a
  short line within the commentary prose (e.g. `ओं ॥ अथातो ब्रह्मजिज्ञासा ॥ १-१-१ ॥` at
  `sribhashya-01-01.md:638`), surrounded by bhāṣya prose. 32 `# Sutra` headings per
  `sribhashya-01-01.md` (545 total across the 16 files per PROVENANCE). The mūla sūtra is present but
  **interleaved with commentary** — extraction requires parsing each Sutra passage to isolate the
  sūtra line from the prose.

**Conclusion:** mūla Gītā and mūla Brahma Sūtra are **not present as standalone texts** in
`structured_md`. They exist only *embedded* inside Rāmānuja's bhāṣyas. Ingesting them as separate
texts therefore requires **one of**:

1. **Extracting the mūla from the bhāṣya files** (a new extraction task — non-trivial for Brahma
   Sūtra because the sūtra is inline in prose; feasible for Gītā via the converter's mūla-line
   heuristic), or
2. **Sourcing standalone mūla editions** from elsewhere (e.g. Gītā mūla from a separate source, mūla
   Brahma Sūtra likewise) and converting them through the normal md2json path.

This is a **sourcing/derivation gap**, not just an ingestion step. Step 3 below is revised
accordingly.

**Mūla texts and the category model — REVISED (scope update):**

The user's scope update adds mūla Gītā and mūla Brahma Sūtra as texts. These do not fit the
"upanishads"/"ramanuja" axis cleanly, so the category model must be reconsidered. This is **not** a
default "bolt on a third category" decision; the two-category model was already narrower than the
corpus. Options, assessed:

1. **A third category "mūla"/canonical (e.g. "mūlagranthāḥ" or "canonical")** housing mūla Gītā +
   mūla Brahma Sūtra (+ potentially the Upaniṣads' mūla, which currently live under "upanishads").
   - Pros: simple, gives mūla texts a discoverable home.
   - Cons: "mūla" is a *relationship* (mūla/bhāṣya) as much as a category; a generic "canonical"
     bucket becomes a catch-all as more śruti/smṛti arrive; it does not express *which* text is the
     mūla of *which* bhāṣya.
2. **"Commentary-on" as a relationship, not a category.** mūla/bhāṣya is expressed as a link
   (`commentary_on` / `based_on`) between two texts — e.g. `gita-bhashyam` → `gita`,
   `sribhashya`/`vedanta-deepam`/`vedanta-sara` → `brahma-sutra`. Categories remain the discovery
   axis.
   - Pros: semantically correct; scales to any depth of commentary (sub-commentaries); keeps
     "ramanuja" as an author/tradition category without forcing every Rāmānuja work into a
     "mūla" bucket.
   - Cons: requires a new relationship field (schema + indexer + possibly UI), which is more
     machinery than the v1 chips need.
3. **Work-family categories** (recommended hybrid): categories are per *work-family* — e.g.
   `gita` (mūla Gītā + gita-bhashyam), `brahma-sutra` (mūla BS + the 3 bhāṣyas), `upanishads`
   (existing), plus `ramanuja` as an *author* category that overlaps. Mūla Gītā → `["gita"]`;
   gita-bhashyam → `["gita", "ramanuja"]`; mūla BS → `["brahma-sutra"]`; sribhashya →
   `["brahma-sutra", "ramanuja"]`. This uses the already-decided overlapping-tags model (§2.5),
   gives mūla texts a natural home, and lets the "ramanuja" chip still show all of Rāmānuja's works.
   The mūla/bhāṣya relationship is *implied* by co-membership and can be made explicit later.

**Recommendation:** **Option 3 (work-family categories).** It leverages the existing
overlapping-`categories` design, avoids a semantically-empty "mūla" bucket, and does not require a
new relationship field in v1. If the mūla/bhāṣya link later needs to be explicit (e.g. for a
"see commentary" affordance), a `commentary_on` field can be added without re-architecting
categories. This also cleanly answers "where does mūla Gītā live?" — under `gita`, alongside its
bhāṣya.
